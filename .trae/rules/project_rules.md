# LegalMind 项目文档管理规则

## 核心约定

本项目有两份核心 Markdown 文档，用途严格区分，不可混淆：

### 1. `UPGRADE_PLAN.md` — 改造计划（待做 + 参考资料）

**定位**：项目的"技术路线图"，记录所有计划要做的优化和新增功能。

**写入内容**：
- 待实现的功能规划（标注预估工时或优先级 P0-P3）
- 每个功能项的"业务背景"、"做法/伪代码"、"通用概念"、"通用价值"
- 已完成的功能项标记 ✅，保留原始规划文字供回溯
- 参考 LangGraph/LangChain 官方文档、GitHub 热门项目的好 API 和最佳实践
- 末尾维护"优化优先级总览"表格

**写入风格**：
- 每个功能项先讲"业务背景"（为什么要做），再讲"做法"（怎么做），再讲"通用概念"（换框架也能用的知识）
- 不追求代码完整，追求概念清晰
- 引用外部资料时附链接

### 2. `优化项目.md` — 优化方案（已完成 + 待办）

**定位**：项目的"执行日志"，记录实际做了什么、修复了什么、还剩什么没做。

**写入内容**：
- 已完成的功能（标注 ✅，附简要说明：改了什么文件、解决了什么问题）
- 已修复的 Bug（标注 ✅，附根因和修复方式）
- 未完成的功能（保留【待做】标签 + 优先级）
- 文件顶部"最近更新"摘要行，记录最近几轮改动

**写入风格**：
- 极简：每项一两行 + 关键文件引用
- 已完成项附文件路径链接
- 不写伪代码，不写概念讲解（那些在 UPGRADE_PLAN.md 里）

## 同步规则

当完成一个功能或修复一个 Bug 时，**两份文档都要更新**：

| 场景 | UPGRADE_PLAN.md | 优化项目.md |
|------|-----------------|-------------|
| 新增一个规划项 | 新增章节 + 概念讲解 | 不动 |
| 完成一个功能 | 该项标记 ✅（保留原文） | 新增 ✅ 条目 + 文件引用 |
| 修复一个 Bug | 不动（除非是架构级 Bug） | 新增 ✅ 条目 + 根因说明 |
| 发现新问题/新优化点 | 新增章节 + 概念讲解 | 新增【待做】条目 |

## 文档更新清单

每次修改代码后，检查是否需要更新以下文档：

1. `UPGRADE_PLAN.md` — 改造计划
2. `优化项目.md` — 优化方案
3. `README.md` — 项目总览（功能特性、架构图、API 列表）
4. `backend/README.md` — 后端文档（架构、环境变量、组件）
5. `frontend/README.md` — 前端文档（组件、状态、交互流程）
6. `CHANGELOG.md` — 变更日志（版本号 + 新增/修复/变更）
7. `CLAUDE.md` — AI 上下文文件（目录结构、架构图、常用命令）

## LangGraph/LangChain 代码规范

- async 函数中禁止同步阻塞调用，用 `asyncio.to_thread` 包装 CPU 密集型操作
- 循环节点必须有退出条件（如 `MAX_ROUNDS` 常量），防止无限循环
- interrupt 数据结构必须兼容前端 `InterruptCard.vue` 的 `{"type": ..., "question": ...}` 格式
- 子图状态用 `TypedDict` 定义，内部字段不暴露给主图
- 条件边路径函数返回值应为节点名本身，避免冗余 path_map 映射
